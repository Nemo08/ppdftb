# doc_pdf.md — накопленные знания по PDF, unipdf и пакету pdfpl

Конспект опыта разработки шаблонизатора PDF (`pkg/pdfpl`): как устроен контентный
поток PDF, как с ним взаимодействует unipdf, какие подводные камни встречены в
боевых шаблонах MS Word и как они исправлены. Материал накапливался в течение
сессии разработки (диагностика `Test.pdf` / `Test2variant.pdf`).

---

## 1. Обзор пакета pdfpl

Пакет — аналог `go-template-docx`, но для статических PDF-шаблонов. Он:

1. Читает PDF файла средствами **unipdf** (`github.com/oliverpool/unipdf/v3`).
2. Для каждой страницы склеивает все контентные потоки в одну строку.
3. Разбирает эту строку собственным лексером/gрамматиком (unipdf тут не
   используется — свой токенизатор).
4. Находит плейсхолдеры `{{.Key}}` / `{{Key}}` в **логическом тексте** ранов.
5. Планирует правки (подмена операндов показа, переименование шрифтов,
   расширение клеток, доводку линии) в координатах исходного потока.
6. Применяет правки справа налево и отдаёт поток на запись через unipdf.

Key-точки входа:

| Символ | Назначение |
|---|---|
| `Replace(params *ReplaceParams)` | чистый поток → поток, без файлов |
| `ReplaceFile(ctx, input, output, values)` | PDF-файл → PDF-файл с внедрением шрифтов |
| `ListPlaceholders(stream)` | диагностика: какие ключи ждёт шаблон |
| `ValuesFromXML(r)` | плоская карта из XML (формат wconv) |
| `GlyphWidth`/экспорты `FontCmap`, `CoveredBy`, `BaseFontName`, `IsCompositeFont` | диагностика |

## 2. Контентный поток PDF: базовые операторы

Контентный поток — последовательность операторов (`BT … ET` — текстовый объект):

```
BT
  /F1 12 Tf        % выбрать шрифт и размер
  50 700 Tm        % абсолютное позиционирование (X Y Tm)
  (французских булок, да ) Tj      % показать строку
  [ (कुछ) -3 (текст) ] TJ          % массив: строки и кернинги чисел
ET
```

Ключевые операторы для нашего дела:

- `Tf` — «font size Tf»: два токена операнда (имя `/F1`, число) предшествуют
  оператору. Это единственный способ узнать активный шрифт рана.
- `Tj` — показать одиночную строку-литерал `(…)` или `<(hex)>`.
- `TJ` — показать массив `[ (a) -12 (b) … ] Tj`: строки и числа-кернинги вперемешку.
  Число в массиве — отрицательный сдвиг влево (в 1/1000 em) перед следующим глифом.
- `Tm`/`Td`/`TD` — сдвиг либо абсолютная установка текстового курсора:
  `X Y Tm` (MS Word позиционирует каждый фрагмент **абсолютно**: `... E F Tm`).
- `re`/`W*`/`n` — прямоугольник (`x y w h re`), клип (`W* n`): клетки таблицы Word.
- `BT`/`ET` — границы текстового объекта; вне его показ игнорируется.

## 3. Лексический анализ (stream.go)

Собственный токенизатор, чтобы точно знать байтовые границы объектов:

- Типы токенов: число, строка, hex-строка, имя (`/F1`), `[`, `]`, словарь `<<…>>`,
  оператор (любое слово).
- Пробелы-разделители: NUL, HT, LF, FF, CR, SP (ISO 32000 §7.2.2) — `isWs`.
- Разделители (delim): `()<>[]{}/%` — завершают токен без пробела — `isDelim`.
- `(…)` литерал: escape `\n \r \t \b \f`, `\\`, `\(`, `\)`, восьмеричные `\ddd`
  (байт от 0 до 255 — так MS Word кодирует Cyrillic в WinAnsi-строках) — `bindEscape`.
- `<hex>` строка: чётное число hex-цифр, при нечётном дополняется нулём справа;
  пробелы внутри допустимы и отбрасываются — `decodeHex`/`hexNibble`.
- `<<…>>` словарь: для шаблонизатора непрозрачен; важно лишь корректно найти
  закрывающий `>>`, минуя строки с `<<`/`>>`/`(`/`<` внутри — `lexDict` +
  `lexDictString`/`lexDictHex`.
- `%` — комментарий до конца строки — `skipComment`.

**Косяк №1: разорванный словарь.** Оптимизатор Acrobat режет контент «по байтам»
и может оборвать последний словарь прямо на границе потока без `>>`. Лексер, если
поток кончился, а глубина словаря > 0, **молча завершает словарь** (история: это
точно безопасно — дальше разбирать нечего).

**Косяк №2: одинокий `>`.** После такого обрыва следующий «фрагмент» потока может
начинаться с осиротевшего `>` от словаря. В `lexWord` слово из одного разделителя
нельзя оставлять «нулевой длины» — иначе лексер зациклится навсегда на этом
символе. Решение: если слово не сдвинулось — продвинуться на 1 символ.

## 4. Раны и извлечение текста (textRuns)

`textRuns(stream)` → `[]streamRun`:

- Проходит по токенам, отслеживая состояние `BT/ET`.
- При `Tf` фиксирует активный `font` и `size` (операнды за 2 токена до `Tf`).
- При `Tj`/`TJ` внутри текстового объекта вычисляет границы операнда
  (`operandBounds`: для `Tj` — от строки до конца оператора, для `TJ` — от `[`
  до конца оператора) и собирает **логический текст** (`extractShowText`).

Структура `streamRun`: `text` (логический), `start`/`end` (байты потока),
`font`, `size`, `opTok` (индекс токена оператора), `opStart`, `opType` (`"Tj"`/`"TJ"`).

> **Почему логический текст, а не байты операнда:** в TJ-массивах MS Word фрагмент
> `{{.ESYear}}` физически разбит на литералы `[({{.) 4 (ESY) …]`, и скобки `{{`
> `}}` не соседствуют в байтах. Только конкатенация литералов массивов (в порядке
> следования) даёт читаемый плейсхолдер.

Для Composite/Identity-H ранов числовой токен-кернинг в массиве сдвигает следующий
символ — при конкатенации порядок строк массива сохраняется (идём от `[` вперёд).

## 5. Поиск плейсхолдеров

Regex: `\{\{\s*\.?([^{}\r\n]+?)\s*\}\}` — ловит `{{.Key}}` и `{{Key}}` с
необязательными пробелами. Имя ключа в regex «голое» — точка-префикс поддерживается
как необязательный элемент до `\s*`.

`findFields`:

- Применяется к **логическому тексту ранов**, а не к байтам операнда.
- Полностью пропускает range-блоки `{{range …}}...{{end}}` (сквозные и в одном
  ране, и расползающиеся по многим ранам).
- `collectFields` дополнительно считает байтовые смещения begin/end — они
  **приблизительные** (для `TJ` кернинг не учитывается) и носят диагностический
  характер; для сборки (`replaceCrossRunFields`/`segOfRun`) используются только
  `key` и `run`.

**Важно:** `findFields` видит только однорановые плейсхолдеры. Межрановые
(фрагменты по ранам) ищутся отдельно — см. §11.

## 6. MS Word: как он генерирует PDF (корень почти всех косяков)

Боевые шаблоны сделаны в Word. Его контентный поток устроен специфично:

1. **Каждый фрагмент линии в отдельном BT/ET** с абсолютным `X Y Tm`. Текст показа
   может быть разбит на много мелких ранов даже внутри одного слова.
2. **Плейсхолдер разнесён по ранам.** Например `{{.Test}}` — по одному символу
   (или по несколько) в каждом ране: `{(}{{)`, `{.}`, `{T}`, … В итоге и `{` и
   `}` живут в разных ранах — это **межрановый (cross-run) плейсхолдер**.
3. **Статичный текст и `}}` в одном ране.** Хвост абзаца после поля часто слит с
   закрывающими скобками: `R8: "}} французских булок, да "` — юстировочный сдвиг.
4. **Клеточные клипы.** Каждое поле Word — прямоугольник `re` + клип. Длинное
   значение в клетке нуждается в расширении `re`, иначе обрезается справа.
5. **Хвостовые пробелы клетки.** После значения (а иногда и до) в потоке сидят
   ран-блоки из одних пробелов на том же базлайне, визуально перекрывающие внедрённое
   значение — с виду «сбитый кернинг». Это **whitespace-only раны**.
6. **Центрированные абзацы.** Word рефлоуит центрированную строку: если внедрить
   более широкое значение, строка «расползается» вокруг центра, если не сдвинуть Tm.

## 7. Шрифты в PDF: простые, композитные, сабсеты

### Типы, встречающиеся в шаблонах

- **Простой TrueType (simple, WinAnsi)** — `/F1` с Subtype TrueType. Байт в
  строке — это код символа. Кириллицы в глифах нет физически (глифы только Latin),
  плюс WinAnsi-кодировка. Вставить русское значение «такими байтами» нельзя.
- **Композитный CID (Subtype Type0, Encoding Identity-H)** — двухбайтовые коды
  `(hex)`. Используется Word для сабсетов (например `/XOThames`).
- **Сабсет:** имя BaseFont имеет префикс `NNNNN+` (5 символов + `+`) — `logicalFor`
  отрезает его. CID — это **номера глифов мини-сабсета**, а не Unicode; однозначно
  восстановить текст можно только через **ToUnicode CMap** (может отсутствовать у
  Acrobat-оптимизированных файлов).

### Как работать с текстом шрифта

- `RunesToCharcodeBytes([]rune)` → `(bytes, miss)`; `miss == 0` — все руны
  покрыты — это и есть «шрифт покрывает текст» (`coveredBy`/`fontCovers`).
- `StringToCharcodeBytes(text)` — кодирование «нативным алфавитом» (для
  Composite — двухбайтовые CID).
- `GetRuneMetrics(rune)` → `CharMetrics.Wx` — ширина в тысячных долях em;
  `runeWidth` суммирует их по тексту.

**Вывод:** если шрифт рана не покрывает значение целиком (`miss != 0`) — ран надо
**переключить на внедрённый TrueType** (единственный надёжный путь для русского
текста).

## 8. Внедрение TrueType-шрифта (fonts_pdf.go)

Стратегия рендера значения внедрённым шрифтом:

1. Подобрать системный `.ttf` под логическое имя BaseFont рана (см. §9).
2. Прочитать его unipdf'ом в `model.PdfFont` (unitype для парсинга программы).
3. Вставить шрифт в ресурсы страницы под новым именем `/TFx`
   (`pageFontContext.register`), один объект шрифта на семейство через
   `fontManager` (лениво, после всех страниц — `subsetAll`).
4. В потоке: переименовать `Tf` рана `/F1 → /TF1` (`editRange` по `fontNameRange`).
5. Текст вставить **hex-литералом двухбайтовых CID**: `<…> Tj`, ширина — реальные
   метрики внедряемого шрифта. Так для Identity-H печатается форма `<...>`.
6. Построить и прикрепить к объекту шрифта **ToUnicode CMap** и **Widths** —
   иначе поиск/измерение текста в родительских программках (например наш же
   шаблонизатор на прогонке результата) даст неверные результаты.
7. Сабсетить шрифт до использованных глифов после обработки всех страниц
   (`fontManager.subsetAll`) — размер файла не раздувается.

Кодек (`RunCodec`) инкапсулирует: `Encode`, `Hex()`, `Width` (исходный шрифт),
`NewWidth` (внедряемый), `FontName` (`/TF1` либо `""` для originalCodec).

### Косяк про originalCodec

Если шрифт рана **уже покрывает** значение (обычный Latin), переключать его не
нужно. Тогда используется `originalCodec` (кодирует нативным алфавитом, ширины
`0`). **Важно:** при контейне эвристическом пути без кодека и с кодеком `FontName==""`
компенсация ширины считается по-разному — `FontName != ""` даёт компенсацию,
`originalCodec` — нет (текст в родном шрифте уже занимает натуральную ширину).

## 9. Подбор системного шрифта (findFontByName / findFontCovering / resolveEmbeddedFile)

### Каталоги (`systemFontDirs`, cross-platform)

- `%WINDIR%\Fonts` и `%SystemRoot%\Fonts`.
- `%LOCALAPPDATA%\Microsoft\Windows\Fonts` — пользовательские шрифты.
- **`%LOCALAPPDATA%\Microsoft\FontCache\4\CloudFonts`** — cloud-шрифты Microsoft 365
  (например **Aptos**): имя семейства = **имя подкаталога**, файлы начертаний внутри
  — с числовыми именами без расширений.
- `%ProgramFiles%\Microsoft Office\Fonts` и `…\Microsoft Office\root\Fonts` —
  шрифты Office, установленные в папку программы, а не в Windows\Fonts.
- `/usr/share/fonts/...` (Liberation, MSTT, DejaVu) — Linux-фолбэк.

**Косяк №3 (фикс этой сессии):** Aptos в системе почти наверняка лежит ТОЛЬКО в
CloudFonts (Win10 без локальных пакетов семейства), а не в Windows\Fonts. Пока
`systemFontDirs` не заглядывал в CloudFonts и `findFontByName` фильтровал файлы по
**имени файла** — Aptos не находился вовсе, и значения падали в фолбэк «а что
есть». Исправлено: (а) CloudFonts и Office Fonts добавлены в перечень каталогов;
(б) в `findFontByName`/`findFontCovering` каталоги-семейства обходятся целиком
(семья = имя подкаталога); (в) `resolveEmbeddedFile` скорит вес/начертание.

### Нормализация имён

- `fontNorm`: только `[a-z0-9]`, регистр в нижний: `"XO_Thames_Bu"` ≡
  `"xothamesbold"`.
- `fontFamilyOf`: от PostScript-имени до первого дефиса (стиль отделён дефисом:
  `XOThames-Bold`), затем срезка хвостового `mt` (`TimesNewRomanPSMT` →
  `timesnewromanps`). Так `XOThames-Bold` и `TimesNewRomanPS` сводятся к семье.
- `fontBoldish`/`italicish`: поиск токенов (`bold`, `black`, `heavy`, `bd`,
  `italic`, `oblique`, …) в нормализованном имени.

### Порядок подбора

`resolveEmbeddedFile(logical, text)`:
1. `findFontByName(logical)` — точное совпадение семьи + веса + начертания среди
   установленных (разбор файла через unipdf, кандидаты хинтом по имени файла или
   подкаталогу);
2. иначе `findFontCovering(bold)` — «до того, что есть», но с приоритетом: для
   жирного логического запроса сначала `bold`-файлы, затем `black/heavy/bd`, затем
   остальные; курсор/прямой стиль запроса не подменяется противоположным;
3. иначе `""` — остаётся оригинальный шрифт документа.

Никаких захардкоженных имён шрифтов и завязки на Windows-реестр.

## 10. Компенсация ширины (генерация TJ с кернингом)

Чтобы **следующий после плейсхолдера текст не поехал**, замена сохраняет ширину:

```
delta = ширина(плейсхолдер) − ширина(значение)
```

и если `delta > 0`, операнд печатается как TJ-массив с числом `-delta`:

```
[(значение) -delta] TJ
```

Число в TJ-массиве — сдвиг влево (отрицательное число «догоняет» текст). Отрицатель
сдвиг компенсирует, если значение УЖЕ. Если значение шире — delta < 0, и без
`AllowWider` замена отменяется целиком (такие попадают в `Skipped`).

Ширины:
- без кодека — эвристика `glyphWidth` (в тысячных em: `I1,.` `278`, цифры 500,
  A-Z `650`, a-z `500`, пробел `278`, прочее `500`);
- с кодеком — реальные метрики (`Width`/`NewWidth`).

## 11. Межрановые (cross-run) плейсхолдеры

### Обнаружение: `buildCrossRunFields`

Метод «склейка и отображение назад»:

1. Конкатенируем тексты ранов в строку `combined` с мапой «диапазон → ран».
2. Ищем `{{...}}` в `combined` обычным regex, **пропуская range-блоки**.
3. Для найденного диапазона вычисляем пересечение с каждым раном: если затронуто
   > 1 рана — это cross-run поле. Фрагменты-ребра (прихвачен не весь ран) — `partial`.

Однорановые поля здесь отсекаются — они уходят в `segOfRun`. Ключ берётся из
`values`; отсутствующий → `value == ""` → пропуск. **Разные размеры шрифта фрагментов
режут поле целиком** (иначе значение вышло бы разнокалиберным); различия шрифтов
допустимы — значение рисуется шрифтом первого (левого) фрагмента.

### Стратегия замены (основной принцип)

Значение рисуется **один раз — в первом (левом) фрагменте**. Все последующие
фрагменты «схлопываются» с нулевой/компенсирующей шириной, а относительные `Td`
между ранами **НЕ трогаются** (они задают позиции последующего текста строки и
уже учтены геометрией дельты).

Режимы каждого не-первого фрагмента:

- **Полнорановый** (фрагмент занимает весь ран) → замена на пустую строку с
  компенсацией ширины: `[() -width] TJ` (фрагменты сидят в отдельных клетках с
  абсолютным Tm — компенсация возвращает курсор на ширину схлопнутого текста).
- **Частичный, без статики** → `[() 0] TJ`.
- **Частичный со статикой** (статика префикса/суффикса остаётся в ране) →
  `splitRunOperand` режет операнд по границам фрагмента и сохраняет префикс/суффикс
  **verbatim** (собственной строкой-оператором), значение здесь НЕ рисуется.

### Первый фрагмент

- Если первый фрагмент **частичный** (в ране есть статика) — `composePartialRun`:
  префикс (в исходном шрифте) → при необходимости `Tf` на внедрённый шрифт →
  значение → восстановление исходного `Tf` → суффикс. Значение рисуется ровно в
  точке начала фрагмента; ширина поля разнесена по дельте первого фрагмента.
- Если первый фрагмент **полнорановый** и включилось внедрение шрифта — Tf рана
  переименовывается `/F1 → /TF1`; поле расширяется (`planFieldWiden`).

> Больше одного cross-run поля в одном ране (редкий конфликт вёрстки) — такой ран
> пропускается целиком.

## 12. splitRunOperand — резание TJ по фрагменту (и его косяки)

`splitRunOperand(toks, r, lo, hi)` режет операнд показа рана по байтовым границам
фрагмента в декодированном `r.text`:

1. Переводит `lo/hi` в **ран-индексы** (`utf8.RuneCountInString` до `lo`/`hi`).
2. Собирает «сырую длину» литералов операнда (для `Tj` — один литерал; для `TJ` —
   с `[` по `]`). Декодирует **байты на символ**: `total == n*2 → bpc=2` (CID),
   `total == n → bpc=1`; иначе — `ok=false`.
3. Проходит литералы слева направо, определяя зону каждого: префикс (начало рана),
   фрагмент, суффикс (конец рана). Число-кернинг привязывается к **предшествующему
   литералу** — граничный кернинг перед фрагментом попадает в префикс, поэтому
   значение рисуется с той же точки, где в оригинале стоял первый глиф поля.
4. Готовые префикс/суффикс собираются потоково-гексом/строкой (`writeLiteral`).

**Косяк №4 (фикс этой сессии, `Test2variant`): ** если сопоставить границы
фрагмента с токенами не удалось (`ok=false`) — поле надо **пропустить целиком и
откатить уже накопленные правки этого поля** (запоминаем `baseEditsLen` до цикла по
частям и восстанавливаем `edits[:baseEditsLen]`). А до фикса `splitFailed` просто
обрывал ран одиночным `[() 0] TJ`, затирая статику — хвост строки исчезал
(«французских булок, да…» не печатался).

## 13. Доводка линии (line-fit): центрирование и пробелы

После замены широким значением работают две доводки:

### `voidOverlappedSpaces`

Обнуляет whitespace-only раны сразу за полем на том же базлайне, перекрывающие
интервал `[leftX + dx, leftX + dx + newPts]` — заменяет их на `[() 0] TJ`. Иначе
пробелы Word-клетки рисуются поверх текста — «сбитый кернинг».

### `lineShiftEdits` (центрированный рефлоу)

Если значение **шире** плейсхолдера (`dx = (origPts − newPts)/2 < 0`), строка,
**горизонтально центрированная на странице**, сдвигается влево на `dx` — так Word
рефлоуит центрированные абзацы. Критерий центрирования: центр линии (от первого
Tm рана до конца текста строки) близок к центру страницы (±30pt). Для
лево-выровненных строк и строк в колонках сдвиг НЕ делается. Сдвиг — правки токена
`X` у `Tm` каждого рана строки.

Применяется только если поле — **единственное непустое** содержимое строки
(иначе строка остаётся лево-якорённой, как в шаблоне).

### `planFieldWiden`

Расширяет клетку (`re x y w h`), если натуральная ширина значения
`x0 + advPt + 1` превышает правую границу текущего поля: правит токен `w`.
Нужно, чтобы длинный текст не обрезался у правого края клетки и буквы не налезали.

## 14. Координаты: откуда берутся X/Y и как с ними работать

- `penXY(toks, r)`: предпоследний и последний числовые операнды последнего
  перед показом `Tm`/`Td`/`TD` — это `(X, Y)` начала рана. Для `Tm` это абсолютная
  точка, для `Td/TD` — относительная, но MS Word использует `Tm`.
- `tmXToken`: индекс токена `X` этого оператора (для сдвига при центрировании).
- `tfTokens`/`fontNameRange`: индексы токенов имени/размера последнего `Tf` перед
  показом.
- `cellRect(toks, r)`: идём от оператора показа назад до последнего `re`; берём
  прямоугольник, в который попадает начало рана (`x0 ∈ [cx−0.5, cx+cw+0.5]`);
  возвращает координаты и индекс токена ширины.

**Важно:** все эти проходы работают **назад от `opTok`**, а не вперёд — последний
встреченный оператор до показа и есть активный.

## 15. Модель правок: editRange и применение справа налево

- Все правки (подмена операндов, переименования Tf, изменение токенов Tm/w,
  доводки) планируются в **координатах исходного потока**.
- `editRange{start, end, to}` — точечная замена байтового диапазона.
- `applyEdits` сортирует по убыванию `start` и применяет сверху вниз: расширение/
  сжатие ранних фрагментов **не сдвигает позиции поздних** — поэтому координаты не
  «поехали» даже при изменении длин.
- Один ран может получить несколько правок (операнд + Tf + клетка), и это
  безопасно, пока диапазоны не пересекаются.

## 16. Файловый слой: ReplaceFile и unipdf

### Склейка потоков страницы

`page.GetContentStreams()` вернёт массив строк. **Acrobat при оптимизации нарезает
контент страницы на фрагменты «по байтам», разрывая операторы и словари на
границах** — поэтому:

```
joined = strings.Join(streams, "\n")   // sep только при len > 1
```

Обрабатываем склейку как единый контент, записываем назад ОДНИМ потоком через
`page.SetContentStreams([]string{out}, core.NewFlateEncoder())`.

> **Почему `\n`:** без разделителя два соседних фрагмента могли бы слипнуться в
> один токен на границе (конец `Tj` оператора и начало следующего операнда).

### Жизненный цикл

1. `model.NewPdfReader(f)` → цикл по страницам, `reader.GetPage(p)`.
2. На странице: `newPageFontContext(fm, page)` → `provider()` (кодеки) и `decoder()`
   (трансляция логического текста: hex-CID → Unicode для Identity-H, чтобы
   `findFields` увидел `{{.Key}}`).
3. `Replace(...)` c `AllowWider: true` (файловый слой всегда разрешает выход вправо).
4. Если ничего не менялось → атомарное копирование исходника в выходной.
5. `fm.subsetAll()` → `writeResult`: `model.NewPdfWriter()`, `pw.AddPage(page)` на
   каждую, `fileutil.WriteFileAtomic(output, …)`.

### Атомарность и безопасность

- `input == output`: пишем через временный файл (WriteFileAtomic) — исходник не
  повреждается даже при падении.
- `context`: каждая страница проверяет `ctx.Err()`, прерываются циклы и запись.
- Все ошибки обёрнуты в контекст (`fmt.Errorf("pdfpl: страница %d: %w", …)`).

## 20. Полезные рецепты «на память»

1. Токен имени шрифта `Tf` ищем за 2 токена до оператора: `[name size Tf]`.
2. Позицию рана — за 2 токена до `Tm`/`Td`/`TD`: `[X Y op]`.
3. Число в TJ-массиве работает в 1/1000 em: кернинг `-delta` = «сдвинуть влево на
   delta/1000 размера шрифта» (для нашего кода delta уже в тысячных em при
   `size/1000` — используем как есть).
4. Вставляя гекс-литерал двухбайтового CID, НЕ забыть подменить Tf ран на
   внедрённый шрифт — байты hex-литерала интерпретируются исключительно текущим
   Tf; иначе CID-байты уйдут в некомпозитный шрифт и распечатаются мусором.
5. `Width`/`NewWidth` в тысячных em; перевод в точки — `width/1000 * size`.
6. Пропущенный плейсхолдер (ключ не найден / значение шире) визуально остаётся
   `{{.Key}}` в готовом PDF — это ожидаемо; `Skipped` считает такие случаи.
7. `decode`: Hex-CID → Unicode применяется к логическому тексту ран ПЕРЕД
   `findFields`, чтобы `{{.Key}}` в CID-сабсетах был виден.
8. `paragraph` (range-блоки) полностью игнорируются: их содержимое НЕ заменяется —
   политика аналога go-template-docx.
